## Candidate evidence and protected diagnostics

| Candidate and source evidence | Benefit and limitations | Failure, privacy, recovery and cost to evaluate |
|---|---|---|
| **Application evidence plus MariaDB InnoDB transaction.** MariaDB describes InnoDB as transactional with crash recovery; Laravel exposes transaction handling. [MariaDB InnoDB](https://mariadb.com/docs/platform/mariadb-faqs/storage-engines/innodb-storage-engine); [Laravel database transactions](https://laravel.com/docs/12.x/database#database-transactions). | Candidate for committing required application evidence with the owning action in one verified transaction/connection using transactional storage. It can capture the application's individually authorized actor and business context, unlike database activity alone. Neither framework API nor database transaction proves the proposed event content, access policy or tamper resistance. | An evidence write failure before commit must not produce established success or partial state; an ambiguous commit needs authoritative reconciliation. MariaDB identifies statements that cause implicit commits, so transaction boundaries and storage engines must be checked, including DDL and mixed stores. [Implicit-commit statements](https://mariadb.com/docs/server/reference/sql-statements/transactions/sql-statements-that-cause-an-implicit-commit). More write volume, storage, backup and access administration are expected; measure rather than assume cost. Durability depends on configuration and infrastructure; [MariaDB describes commit-flush trade-offs](https://mariadb.com/docs/server/server-usage/storage-engines/innodb/innodb-system-variables#innodb_flush_log_at_trx_commit). |
| **MariaDB Community Audit Plugin.** It records configured connection, query and table activity to file or syslog; [MariaDB plugin documentation](https://mariadb.com/docs/server/reference/plugins/mariadb-audit-plugin/mariadb-audit-plugin-log-settings) describes its event choices. | May supplement protected technical monitoring of database access. Database identity can be a shared application account rather than the individual business actor; query execution is not proof that the containing business transaction committed. It cannot alone satisfy the required application evidence contract. Plugin availability and its failure behavior require version/profile-specific evaluation. | Query logging can expose plaintext data and secrets, including unsuccessful queries; MariaDB warns about sensitive query contents and incomplete password masking. [Log format](https://mariadb.com/docs/server/reference/plugins/mariadb-audit-plugin/mariadb-audit-plugin-log-format). Event filtering, restricted file/syslog access, capacity, rotation, monitoring and restore add workload and may omit needed context. Do not install or enable it based on this comparison. |
| **MariaDB Enterprise Audit.** MariaDB documents filters and reports query audit messages at query completion rather than transaction completion. [Enterprise Audit](https://mariadb.com/docs/server/reference/plugins/mariadb-enterprise-audit). | Additional technical monitoring candidate, not application attribution or a committed-outcome record. Enterprise availability, licensing/contract and compatibility must be investigated for a real supported profile; no pricing is assumed. | MariaDB warns that audit data can contain sensitive information, that database-server compromise can affect its integrity, and that protection, retention and backups need attention. Independent custody may reduce a common compromise boundary but increases administration, transfer and privacy exposure. No remote service or new collection is approved. |
| **Laravel log channels for diagnostics.** Laravel documents single-file and daily rotating channels, file permission options and configurable retention. [Laravel logging](https://laravel.com/docs/12.x/logging#configuring-the-single-and-daily-channels). | A local diagnostic channel could be operationally simpler than an external service and support privacy-minimized signals. Rotation, file permissions or a default retention value do not establish required audit retention, tamper resistance or a business transaction boundary. | Review redaction, public neutral failures, filesystem access, capacity, failed writes, rotation and backup copies. Defaults are not approved policy. Context, exception traces, failed jobs and provider responses can contain personal data or secrets. Do not let diagnostic rotation delete required audit evidence. |

**Evidence access:** Viewing and exporting are separate, attributable permissions; server-side scope applies to list/detail/filter/direct access and restored evidence. A database, log or backup custodian is not automatically authorized to inspect client records. A separate archive, append-only controls or integrity checks are candidates, not proofs against privileged alteration: evaluate actual actor/custody separation, protection, correction provenance, access, capacity and restore. Required audit persistence and ordinary diagnostics have distinct failure policies; no universal shutdown or silent fail-open rule is selected.

## Notification recovery candidates

| Candidate and documentation | Advantages and failure limits | Costs, privacy and decision evidence |
|---|---|---|
| **Laravel direct send or queue dispatch after commit.** Laravel documents that queued jobs dispatched before commit may run before data becomes visible, and that `after_commit` defers dispatch until parent transactions commit. [Laravel queues: jobs and transactions](https://laravel.com/docs/12.x/queues#jobs-and-database-transactions). | Avoids dispatching work for a rolled-back transaction when correctly applied. **Inference:** a process failure after commit but before a deferred dispatch is durably recorded can leave an eligible notification without work; the documented ordering alone is not a durable intent or end-to-end delivery guarantee. Direct transport timeout may be ambiguous. | Fewer components initially but needs a demonstrated independent reconciliation path. Log only necessary processing information. Before approval, prove recovery of missed intent and avoid duplicate business commands and notifications. |
| **MariaDB transactional intent plus separately processed Laravel database queue candidate.** InnoDB can coordinate data writes in one transaction; Laravel supports relational database queues and worker processing. [MariaDB transaction](https://mariadb.com/docs/server/reference/sql-statements/transactions/start-transaction); [Laravel queues](https://laravel.com/docs/12.x/queues). | A purpose-limited intent persisted with a committed eligible action is a candidate for later recovery, with a worker consuming it independently. Merely choosing Laravel's database queue does **not** prove queue insertion shares the business transaction, or that `after_commit` makes intent atomic; verify actual connection, transaction and implementation. Account and guest email triggers have their own authorized boundaries. | Adds database state, worker supervision, deployment and recovery duties. Outage/full storage, worker crash, stale eligibility and ambiguous provider submission need explicit handling. Queue payloads and failed-job records may hold recipients, content or secrets; minimize and restrict them, with qualified retention review. Transactional intent is not exactly-once delivery. |
| **Separate queue backend or managed transport, with coordinated intent/reconciliation.** Laravel supports multiple queue backends and mail transports, including failover configurations. [Laravel queues](https://laravel.com/docs/12.x/queues); [Laravel mail failover](https://laravel.com/docs/12.x/mail#failover-configuration). | Separating processing can reduce contention on the application database and a failover transport can offer another send path. Neither capability makes a cross-system write atomic, proves inbox delivery or resolves ambiguous sends. Failover after a timeout can duplicate a message if the first transport accepted it. | Additional service, credentials, process ownership, support and possibly fees; every primary and backup provider must independently pass applicable privacy/security, terms, location, availability, retention and exit review before adoption. Actual price and service behavior are unverified. |
| **Authoritative-record reconciliation without separately persisted intent.** | Avoids a dedicated intent record, but must reliably reconstruct permitted events, recipients, content and prior processing. A scan cannot distinguish an ambiguous send from an unsent message unless adequate evidence exists. | Scans and retained history add load and privacy exposure; missing, stale or changed recipient information can cause inappropriate or duplicate messages. Compare its recoverability and evidence burden against persisted intent using real profiles before any decision. |

Laravel documents worker retry and timeout interaction: unsuitable ordering can allow a job to be processed twice; failed jobs require operational handling. [Laravel queue timeouts and failed jobs](https://laravel.com/docs/12.x/queues#job-expirations-and-timeouts). This is not an approved retry value or proof that duplicates are eliminated. Any notification retry operates independently of the committed booking command. A provider request, queue acceptance or transport acceptance is not inbox delivery, reading, identity proof or a guarantee. Exact status vocabulary and provider event interpretation remain open.

## Cross-boundary failure analysis

| Event | Expected boundary / future evidence |
|---|---|
| Audit write fails before commit or storage fills | Verify the owning transaction does not establish partial state or report unestablished success; treat diagnostics separately. Preserve mandatory evidence and raise a protected operational condition. |
| Browser response lost after a commit | Reconcile authoritative state; a valid committed notification remains eligible under its approved purpose and recipient rules. Do not retry the business command to repair email. |
| Transaction rejected, held, uncommitted or authoritatively unknown | No transaction success email solely because of uncertainty; reconcile before any unsafe retry. |
| Worker crash, database outage or dispatch gap | Show whether a recoverable eligible intent exists and how processing resumes independently. Do not assume a queue configuration recovers a missing intent. |
| Provider accepts then response is lost; retry/failover | Record uncertainty faithfully; evaluate provider-specific identifiers and signals, duplicate controls and reconciliation. No exactly-once or inbox guarantee follows. |
| Throttling, failure, bounce or out-of-order signals | Keep the business outcome intact, interpret only signals actually established by the provider, and test safe recovery and user-visible next steps. |
| Unauthorized reader/export, credential compromise or restore | Deny cross-scope reads and exports; protect logs, failed jobs and backups, revoke/rotate credentials under an approved incident procedure, and restore restrictions. No automatic business-data access follows technical custody. |

## Conditional recommendations and review gates

**Candidate for further engineering design:** compare application-owned required evidence and purpose-limited notification intent in the same verified InnoDB transaction as the owning action, with independently supervised processing. This is contingent on a compatible supported profile, verified connection/transaction boundaries, fault recovery, privacy review and cost/operations feasibility. Laravel after-commit dispatch may be useful for ordering, but should not be the sole demonstrated durability control. Consider database audit plugins only as separately justified technical diagnostics, not substitutes for application evidence. Select diagnostic logging and any additional archive/provider only after demonstrated need and custody review. None is selected by this document.

Engineering and data-integrity/security reviewers own transaction, tamper and failure design; qualified privacy reviewers own data minimization, notice, retention, access and provider processing assessment. Operations and the actual installation/client/provider owners must allocate custody, worker supervision, incident response and restoration responsibilities. The Product Owner decides material trade-offs, supported profiles, providers and costs. EVD-Q01–Q04 and MAIL-Q01–Q04 remain unresolved. Consult current official provider terms and the eventual exact product/version documentation before selection; no vendor price, processing terms, compatibility or operational behavior has been verified for an installation.

After separate authorization, a verification plan should inject failures before/after commit, evidence/intent persistence and provider submission; exercise lost response, worker/database/provider outage, throttling, failed jobs, duplicate/out-of-order attempts, bounce/ambiguous acknowledgements, retention and restored access. Verify all six purpose/recipient/content contracts and each consumer's end-to-end integration; test server-side reader/export denial, cross-installation isolation, neutral responses and secret-free logs. Record actual configuration, environment, owner and results; use human keyboard, screen-reader, zoom and touch review for applicable status/recovery flows. Test doubles cannot establish real provider delivery, and a successful provider submission cannot establish inbox receipt. No test, security/privacy review, operational reliance, implementation or acceptance is claimed.
