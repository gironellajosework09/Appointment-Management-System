# Targeted architecture evidence D — runtime and recoverability

**Draft, 2026-11-13.** D-111 prioritizes investigation, not selection. D-022 preferred direction, D-023/D-036 conditional Docker, D-083 both hosting models and D-084 one supported-profile principle remain. SDD-025 v0.3 and SDD-026 v0.3 are pending exact review; earlier approvals remain in scope. No installation, operation, test, target or deployment is authorized or claimed.

## Version-specific evidence plan

Use **Laravel 13 / PHP 8.4 / MariaDB Community 11.8** as a *documentation comparison tuple*, not a selected or verified profile. [Laravel 13](https://laravel.com/docs/13.x/releases) lists PHP 8.3–8.5 and security fixes through 2028-03-17; [PHP](https://www.php.net/supported-versions.php) lists PHP 8.4 security support through 2028-12-31; [Laravel's database guide](https://laravel.com/docs/13.x/database) lists MariaDB 10.3+ as a framework-supported range. [MariaDB](https://mariadb.com/resources/blog/announcing-yearly-lts-releases-for-mariadb-community-server/) describes 11.8 as an LTS series. These sources do not prove actual host availability, a current exact patch, PHP extensions, Laravel package compatibility, MariaDB lifecycle at selection, or booking correctness.

Engineering should collect, for each proposed exact framework/PHP/MariaDB/driver/backup-tool version and OS: vendor lifecycle and security dates; supported extension and database combinations; license/maintenance terms; upgrade path; InnoDB isolation, lock/timeout and durability settings; backups and restore compatibility; deployment/worker requirements; hosting availability and full operational cost. Record date, source, exact edition and uncertainty. Verify official current terms again before selection. An older Laravel 12/PHP compatible tuple is a comparator only if its shorter remaining security window meets the proposed lifecycle; do not extrapolate Laravel 12 queue behavior to 13 without version-specific confirmation. A documented compatibility matrix and implementation plan are the smallest next evidence actions; actual setup and tests require separate authorization.

## Profile and recovery scenarios

| Scenario / alternative | Proposed evidence and trade-off | Failure and ownership |
|---|---|---|
| Native client-operated vs provider-operated independent installation | Compare same supported technical profile, operator competence, patch window, local infrastructure and handover; native avoids image lifecycle but requires direct host maintenance. | Client or provider may lack coverage; named installation owner must allocate monitoring, credentials, patching, incident and escalation. Technical custody does not grant client-data authority. |
| Containerized equivalent | Compare only if repeatability, isolation or recovery benefit exceeds image, volume, registry, secret and patch complexity; Docker requires separate D-023/D-036 justification and PO approval. | A reproducible image does not restore database volumes or keys; an outdated image or leaked registry credential remains a risk. No container adoption is implied. |
| Logical consistent export | [MariaDB documents](https://mariadb.com/docs/server/clients-and-utilities/backup-restore-and-import-clients/mariadb-dump) transactional snapshot limits and concurrent DDL risks. Verify complete data and non-database assets, database objects, consistency, restore time and compatibility. | Incomplete objects, mixed storage engines or concurrent DDL can invalidate recovery; restricted encrypted custody, authorized operator and privacy lifecycle review needed. |
| Physical `mariadb-backup` | [MariaDB](https://mariadb.com/docs/server/server-usage/backup-and-restore/mariadb-backup/full-backup-and-restore-with-mariadb-backup) states raw files must be prepared; verify source/tool/target compatibility, keys, complete data and restore time. | Corrupt backup, missing key or incompatible version prevents recovery; prepare and restore evidence must be retained without exposing client data. |
| Base backup plus binary logs | [MariaDB](https://mariadb.com/docs/server/server-usage/backup-and-restore/mariadb-backup/point-in-time-recovery-pitr-mariadb-backup) describes recovery from a base plus logs. Compare achievable recovery point and cost of log capture, storage, keys and staff. | Missing logs or wrong replay point may lose or duplicate state; restrict resumed operation until booking, outcome, audit and notification intents are reconciled. |
| Release rollback | Compare previous artifact/config compatibility with data and any irreversible changes; if not safe, plan authorized restore and reconciliation. | A code rollback cannot reverse an incompatible data change or an already sent message; do not promise restoration or silently reissue commands. |

**Target evaluation inputs:** actual change rate and loss tolerance; capture intervals and verified log continuity; backup size and transfer/storage cost; detection, authorization, provisioning, restore, integrity checking and reconciliation duration; personnel availability; platform failure and privacy boundaries. Record measured distributions only after separately authorized synthetic exercises. PO and actual client/provider owners decide measurable objectives after feasibility; no RPO/RTO or availability value is proposed here.

**Recovery verification:** a synthetic rehearsal verifies only its procedure and test data; D-091 separately requires authorized privacy-safe verification of a particular real client backup before relying on it. Test corrupt/missing copy, absent key/operator, partial restore, stale permissions and ambiguous notification attempts under separate authorization; no execution result is asserted. `SECURITY/OPS-Q01` concerns ownership; `SDD-026/OPS-Q01` concerns supported profile. Both remain open before dependent reliance.
