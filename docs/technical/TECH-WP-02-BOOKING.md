## Relevant MariaDB behavior

| Evidence | Practical implication and limit |
|---|---|
| [Transactions and autocommit](https://mariadb.com/docs/server/reference/sql-statements/transactions/start-transaction): MariaDB describes autocommit as enabled by default, explicit commit/rollback for transaction-safe tables, and implicit commits for listed DDL/administrative statements. | A multi-effect booking needs a proven transaction boundary encompassing the transactional state and required evidence; merely issuing several writes does not make them atomic. DDL and nontransactional effects cannot be assumed to roll back with the booking. Email and external services remain outside. |
| [FOR UPDATE](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/for-update): InnoDB locking reads operate when autocommit is disabled or within a transaction; otherwise the clause has no effect for InnoDB. | If evaluated, confirm the actual connection/transaction scope and every participating write path. Locking currently returned rows alone is not proof that absent rows, overlapping intervals or configuration changes cannot race. |
| [Isolation](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/set-commands/set-transaction) and [InnoDB locks](https://mariadb.com/docs/server/server-usage/storage-engines/innodb/innodb-lock-modes): locks concern index records; behavior depends on isolation, search and indexes. The current isolation documentation describes READ COMMITTED locking reads as not protecting gaps, while REPEATABLE READ uses gap locking in documented cases. | A read of an empty duplicate or resource range at READ COMMITTED cannot by itself prevent a concurrent insert. Under other levels, prove the exact query/index/range behavior and interaction of writers; do not infer full business-predicate protection from an isolation label. Documentation has version-specific sections and wording differences about update/range locks; resolve for the selected release by primary documentation and separately authorized tests. |
| [Constraints](https://mariadb.com/docs/server/reference/sql-statements/data-definition/constraint) include primary, foreign, unique and check constraints; [NULL handling](https://mariadb.com/docs/server/reference/data-types/null-values) permits multiple NULLs in a unique index. The constraint reference says check expressions can be disabled; [foreign key documentation](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/optimization-and-indexes/foreign-keys) likewise identifies a switch for foreign-key checks. | Constraints can defend expressible row/relationship invariants, with correct nullability and configuration. They do not automatically enforce aggregate capacity, interval overlap or policy-specific duplicate windows. Privileged configuration, migrations and restores can weaken enforcement; review and verification must cover them. |
| [InnoDB system variables](https://mariadb.com/docs/server/server-usage/storage-engines/innodb/innodb-system-variables) distinguish deadlock victim rollback from lock-wait timeout, where normally only the statement is rolled back unless the applicable setting changes this. | A caught timeout must not be treated as an already-rolled-back transaction: the eventual implementation must explicitly establish and clean up transaction state. A network failure around commit remains unknown until reconciled, irrespective of a client timeout. |
| [InnoDB status](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/show/show-engine-innodb-status) can show deadlock statements and transaction details. [InnoDB variables](https://mariadb.com/docs/server/server-usage/storage-engines/innodb/innodb-system-variables) also document durability trade-offs for flush settings. | Diagnostics may contain sensitive statements/data and require restricted access, minimization and retention review. Durability depends on actual settings and storage/recovery profile; a successful transaction API call is not proof of restoration or a recovery objective. |

## Candidate-specific comparison

All candidates below are designs for investigation, not complete schema or operational selections. Their success depends on the unresolved business policies and all mutation paths using a consistent authoritative boundary.

| Candidate | Potential benefit | Limits, cost and evidence still required |
|---|---|---|
| **InnoDB transaction with explicitly locked conflict domains** | Shared guard or other authoritative conflict domains could serialize final capacity/resource/policy and duplicate decisions, then commit booking, allocation, required evidence and intent outcome together. Locks make contention explicit. | Coverage must include absence/ranges, all resource combinations, duplicate windows, policy revisions and both old and new reschedule allocations. A narrow slot lock is insufficient. Guard creation and lock order themselves need proof. Long-held or broad locks increase waits, deadlocks and operational load. Verify exact queries, indexes, storage engine, isolation and transaction scope, including failover and maintenance writers. |
| **InnoDB conditional update / optimistic version checks in a transaction** | Affected-row checks can detect contention without holding a read lock throughout decision preparation; can be appropriate where every conflict domain has an authoritative version. | One counter or version does not cover dynamic overlap, duplicate policy, multiple resources or coherent policy changes. All relevant comparisons and writes must be atomic, and conflicts need bounded safe handling and re-evaluation. Retry storms and starvation are possible; unknown commit must first be reconciled. Requires proof of domain completeness and conflict tests, not an assumption that low daily workload implies low contention. |
| **InnoDB SERIALIZABLE with appropriate transactions** | MariaDB documents conversion of plain reads to locking reads at SERIALIZABLE under its stated conditions, potentially reducing some read/write anomalies. | This is not a substitute for proving actual predicates, query plans, concurrent policy changes or external effects. Broad locking and deadlocks may cost more than targeted locking. Review version-specific semantics and access paths and measure behavior only under separate test authority. |
| **Constraints as complementary defense** | Unique reference/operation identity and applicable referential or row conditions may be enforced independently of an application check when precisely modeled. | Unique values with NULL, collation and normalization require explicit treatment. A simple unique key can prohibit allowed warnings or proxy cases; aggregate limits and arbitrary overlapping ranges need another proven mechanism. Errors must roll back the entire intended operation and map to truthful, non-disclosing outcomes. Monitor settings and migration/restore integrity. |
| **Ordered command worker** | A single authoritative sequencer can simplify ordering if all conflicting operations, including configuration and rescheduling, enter the same durable domain. | MariaDB locking/transactions still must protect durable state and outcome. Slot-only partitions can miss cross-slot resource and duplicate conflicts; crash/redelivery, exclusive worker ownership and cross-partition atomicity add infrastructure and staffing burden. No queue, delivery guarantee or partition scheme is selected. |

## Same-intent and recovery analysis

A durable server-side association of an opaque client-generated identifier and outcome, a server-issued receipt, and authorized lookup with assisted recovery are the candidates in [WP-01](TECH-WP-01-BOOKING.md#same-intent-outcome-approaches). MariaDB uniqueness and transaction support may help associate one intent with an outcome, but neither establishes identity, payload equivalence, proof of authority, retention or safe retry by itself. Unique constraints permit multiple NULL values, so any proposed key semantics need explicit non-null and scope analysis. Bind the intended command to an authorized actor or independently proven appointment scope, distinguish the operation identity from a public reference, and handle concurrent same-identifier/different-payload cases without creating another mutation or disclosing an unrelated booking. Retention, expiry, access and recovery remain undecided. Lost or expired correlation must remain unresolved and route to authorized assistance; an empty lookup is not proof of failure.

| Failure | Proposed handling to evaluate | Remaining risk |
|---|---|---|
| Empty duplicate range / concurrent reservation | Enforce the complete conflict domain within the final transaction, rechecking current policy and all allocations; abort all losing effects. | A gap lock, guard or version with incomplete range coverage can miss a competing path. |
| Deadlock or lock-wait timeout | Establish whether the entire transaction actually aborted; explicitly roll back an active incomplete transaction. Only retry after the prior outcome and intent are known and policy/authority are rechecked. | Timeout can leave earlier statements in an open transaction; connection loss near commit leaves outcome unknown. |
| Commit accepted but response lost; concurrent replay | Reconcile the durable authoritative same-intent outcome through an authorized path before a follow-up. A different payload under the same identity needs explicit conflict handling. | Correlation expiry, lost receipts, restore gaps and incorrect authority mapping can prevent safe resolution. |
| Required evidence or second allocation write fails | No success is reported without consistent required evidence; show rollback or another reviewed, crash-safe consistency design. On known reschedule rejection the original remains. | Separate stores and external notifications are not covered by an InnoDB transaction; diagnostics are not a replacement for attributable evidence. |
| Crash, storage failure, restore or configuration change | Halt or safely restrict affected mutations until authoritative state can be established; recover bookings, allocations, intent and evidence coherently with authorized operations. Configuration changes affecting accepted appointments use SDD-022 impact review. | Commit durability depends on actual server/storage configuration; backups may not include acknowledged changes. No RPO, RTO, availability value or operator responsibility is established. |

Protect identifiers, matching attributes, diagnostic SQL and backup copies as potentially sensitive; limit collection and access, avoid exposing duplicate matches or appointment existence, and have qualified privacy/security reviewers assess retention, lookup, replay and operational access. D-108 applies; a public reference or identifier is not authorization. No PH-01–PH-10 review is claimed.

## Conditional direction and outstanding decisions

Investigate an InnoDB transactional design with explicit conflict-domain protection and constraints only for precisely expressible approved invariants, alongside a crash-consistent same-intent outcome association. Favor it only if engineering demonstrates complete coverage across capacity, time/resource overlap, duplicate windows, policy revisions, reschedule, required evidence and every writer, and operations can support the contention, durability and recovery profile. Compare a versioned/conditional alternative and SERIALIZABLE approach against the same scenarios; an ordered worker is viable only if its ownership and cross-domain atomicity can be demonstrated. This is a recommendation for further evaluation, not a choice of database version, isolation, schema, key or mechanism.

Before affected implementation, Product Owner review of SDD-006's exact revision and relevant upstream policy dispositions are needed; engineering must document a version-specific concurrency model and implementation proposal, and named data-integrity/security/privacy reviewers and installation operations owners must review it. Applicable implementation, isolated testing, data processing and operational/release authorizations remain separate. Current official lifecycle, platform compatibility, support terms and actual total cost require evidence for the eventual edition/version and installation. Residual risks are not accepted by this evaluation.

## Future verification — proposed, not run

Use a separately authorized, isolated environment with synthetic data. Record actual MariaDB edition/version, engines, isolation, autocommit, indexes/query plans, relevant constraint, logging/durability settings, client behavior, configuration, authoritative persisted state, reviewer and limitations. Include all authorized paths and configuration/maintenance writers. Inspect bookings, allocations, intent outcomes and required evidence, not responses alone.

1. D-070/AC-005: arrange 50 valid simultaneous distinct requests competing for one remaining capacity unit with explicit duplicate-policy preconditions; exactly one reservation succeeds, the other 49 have safe clear unsuccessful outcomes, and no over-capacity, prohibited duplicate, partial or orphaned state remains. This is a future correctness obligation, not a measured result or latency/availability SLA.
2. Exercise empty and populated duplicate ranges, exclusive and shared resource overlaps, differing index access, capacity changes, concurrent policy changes and all booking paths. Verify allowed proxy/multiple-attendee and warning behavior, blocked duplicates and no unrelated disclosure.
3. Induce deadlocks, statement timeouts, rollback failures, connection loss before/during/after commit, repeated same-intent submissions, mismatched payloads and expired receipts; inspect transaction and durable state after restart. Prove a known rejection preserves the old reschedule allocation and unknown is reconciled before retry.
4. Inject failure at each required evidence and allocation write; verify no false success, partial or orphaned state. Test authority/guest proof, neutral disclosure, protection of diagnostics, and constraint settings and restoration under the approved security/privacy scope.
5. Separately authorize outage, failover and backup/restore exercises in the selected profile, verifying consistency across acknowledged booking, allocation, outcome and evidence. Document actual findings and residual risk; no availability, recovery, privacy or security assurance follows from a contention test alone.
