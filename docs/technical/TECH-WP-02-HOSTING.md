# TECH-WP-02 D — Hosting, backup and recovery evidence

**Draft, 2026-11-13.** D-022 is the preferred Laravel/Blade/Tailwind/MariaDB direction; D-020/D-035 require independent installations/databases, D-083 accommodates client and provider operation, and D-084 establishes one standardized supported profile without selecting it. SDD-025 v0.3 and SDD-026 v0.3 await exact-version approval; earlier approvals remain within their scopes. No implementation, platform, exact version, target or vendor is approved here. Evidence below is documentation, not observed compatibility or recovery.

| Candidate and operation | Benefits, constraints and burden | Failure, privacy and evidence | Conditional recommendation and authority |
|---|---|---|---|
| Native managed-by-client or provider installation: Laravel 13 + supported PHP 8.3+ + MariaDB using a documented supported database version, independently installed per client | Laravel 13 [requires PHP 8.3+ and listed extensions](https://laravel.com/docs/13.x/deployment); PHP's [support table](https://www.php.net/supported-versions.php) must be checked at adoption. Native packages avoid container operations but require host patching, compatible extensions, web server, database, credentials, monitoring and named operators. Version combination is an evaluation example, not a selected baseline; framework support, dependencies, DB driver and database version need confirmation together. | Unsupported or mismatched runtime, missing extensions, insecure host, credential compromise or operator absence can disrupt or expose an installation. Vendor documentation does not prove this application works or any host supports the combination. Costs: operator time, infrastructure, updates and support; actual prices unknown. | Prioritize a minimally composed native profile for compatibility and operational evaluation across both ownership models if both can support it. PO approves material profile and versions as applicable after engineering/security review and actual provider/client feasibility; no OS or hosting provider is selected. |
| Containerized equivalent using Docker | Can package consistent runtime dependencies, but adds image build/provenance, host, patching, secret, persistent storage and orchestration responsibilities. Host/client isolation and recovery are still needed. | Stale images, secret exposure, volume loss and incompatible versions remain possible; image scanning and update/recovery procedures add cost. Documentation evidence for this particular stack is absent. | Keep as alternative only if measurable deployment/recovery benefit justifies added complexity and PO approval under D-023/D-036. No Docker adoption follows. |
| Logical export with `mariadb-dump` vs physical `mariadb-backup` | Logical output is inspectable and may support portable recovery but can be slow for large datasets and requires consistent-snapshot/version review. [MariaDB Backup](https://mariadb.com/docs/server/server-usage/backup-and-restore/mariadb-backup/mariadb-backup-overview) supports physical backups and documents platform/engine limits; preparation, compatible versions and storage add burden. | A successful file copy is not a usable recovery. [MariaDB documents](https://mariadb.com/docs/server/server-usage/backup-and-restore/mariadb-backup/full-backup-and-restore-with-mariadb-backup) that raw physical files require preparation; wrong keys or missing files can prevent restoration. Both contain sensitive data; protect copies, keys and transport, separate custody and verify integrity under reviewed lifecycle policy. | Compare both using the chosen version and expected data volume; prefer physical backup plus separately protected recovery material if a future authorized rehearsal demonstrates feasibility. PO approves material method; security/privacy and actual operations owners review custody and costs. This does not exclude logical export where it proves more suitable. |
| Backup only vs backup plus binary-log point-in-time recovery | A full recovery point is simpler; point-in-time recovery can reduce possible lost changes but requires continuous log capture, protection, retention and operational skill. | Missing logs, incorrect positions, key loss, corruption or replaying unwanted operations defeat recovery. [MariaDB describes](https://mariadb.com/docs/server/server-usage/backup-and-restore/mariadb-backup/point-in-time-recovery-pitr-mariadb-backup) a base backup plus binary logs; this is a capability description, not a measured RPO. | Consider point-in-time recovery only where feasibility, privacy lifecycle and measured loss tolerance justify its burden; PO and installation owners approve objectives and allocation. No cadence or RPO/RTO is set. |
| Artifact/config rollback vs restoring a recovery point | Prior artifact and compatible configuration may reverse an application release with less data loss; restore may address data corruption but can discard later accepted work. | Incompatible data changes, mixed app/database versions, duplicate notifications and replayed stale permissions create risk. Operators must identify irreversible changes and reconcile booking, intent, evidence and notification state before reopening. | Design rollback per change and rehearse under separate authorization; use restore only with explicit authority and a documented recovery point. No rollback guarantee. |

**Candidate evidence:** [Laravel 13's release table](https://laravel.com/docs/13.x/releases) lists PHP 8.3–8.5 and a security support date of 2028-03-17; [its database guide](https://laravel.com/docs/13.x/database) lists MariaDB 10.3+ as framework-supported. These are framework compatibility ranges, not proof that every listed MariaDB release remains security-supported or works with an eventual application. Check current MariaDB lifecycle, extensions, packages and host availability before selection. [MariaDB's dump documentation](https://mariadb.com/docs/server/clients-and-utilities/backup-restore-and-import-clients/mariadb-dump) limits consistent transactional snapshots to suitable engines and warns about concurrent schema changes; capture completeness and external files/secrets need independent review.

**Verification plan, not executed:** inventory supported framework/PHP/extension/DB combinations and support dates from the exact versions; validate client and provider operation, isolation, maintenance, credentials and security. In an authorized synthetic environment, rehearse corrupted/missing backup, key loss, unavailable operator, log gaps, upgrade/rollback incompatibility, restored access restrictions, and consistency of booking, audit and notification intent; measure elapsed recovery and data loss without assuming targets. D-091 separately requires an authorized privacy-safe verification of the particular real client backup before relying on it. A synthetic rehearsal is not that evidence.

**Ownership and decisions:** `SECURITY/OPS-Q01` concerns operational ownership; `SDD-026/OPS-Q01` concerns the supported profile. The PO decides material profile and risk; actual client/provider owners allocate credentials, backup custody, incident response, monitoring, maintenance, restore approval and exceptional access per installation. Applicable PH-01–PH-09 and security review precede affected processing/reliance; PH-10 independent review precedes release as required. Technical custody does not grant business-data authority. Current evidence gives no installation compatibility, cost quote, restore result or service commitment.
