The Registry records the exact approved SDD versions in §§13–14 and confirms that those approvals do not authorize implementation or release ([SDD Registry:L419-L455](../specs/SDD_REGISTRY.md#L419-L455)).

Method:

1. Read the effective and preserved requirement/traceability records, Requirements Governance, Registry, all 27 current SDD files, and the requested Architecture, Backend Schema, Security, TRD and CP11 review.
2. For each requirement identifier, inspect the named SDD’s expected behavior and local acceptance criterion/section. The matrix cites substantive SDD text; Registry mapping by itself was not treated as coverage.
3. Classify the stated design contract only. `COVERED` means the criterion is substantively represented in specification text, not implemented or verified. `PARTIAL` marks substantively incomplete design coverage. `DEFERRED` means an explicit approved deferral. A question/mechanism left open at its recorded stage is not by itself a requirement gap.
4. Compare shared boundaries and ownership across SDDs and the supporting architecture, schema, security and TRD references. Reconcile F1–F17 only where an available source artifact supports the finding.

The first matrix maps each requirement to owning SDD criteria. The reverse appendix below enumerates every current criterion in all 27 SDDs and associates it with the requirement identifiers in its SDD source mapping and effective traceability baseline. Criterion associations are not new approved traceability records. Where an SDD’s source mapping is at whole-specification level rather than criterion-by-criterion, the appendix identifies cross-cutting or source-level association and does not claim a finer approved allocation than the artifact provides. The absent F1–F17 source report still prevents reconciliation of any report-specific trace-row finding to a particular identifier.
