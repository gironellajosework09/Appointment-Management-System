# iTakda architecture and database visualization

**Product Owner review proposal · 2026-11-15 · not approved for implementation.** Open each `.drawio` file in diagrams.net/draw.io; boxes and connectors are editable. These are logical illustrations, not evidence of a deployed or verified system. The proposed schema is intentionally a reviewable **core**, not a complete implementation specification. Every table, field, key, relationship and mechanism in it is a candidate.

## The five views

1. [System and technology](01-system-technology.drawio) — browser, server-rendered application, independent client database and permitted email integration.
2. [Component/module architecture](02-components.drawio) — logical responsibilities and the shared final integrity boundary; the boxes need not become packages or services.
3. [Proposed relational ERD](03-proposed-erd.drawio) — candidate core entities, identifiers, relationships and constraints for one client database. Labels on relationships read from the one-side to the many-side; optional intent links are summarized by a dashed line. Consult the dictionary below for details and omissions.
4. [Booking transaction sequence](04-booking-sequence.drawio) — a successful creation's logical path, with rejection and unknown-outcome notes. It does not choose a lock, retry or email-delivery algorithm. [Sequence source](sequence-input.json) permits regeneration with the installed draw.io skill's sequence tool.
5. [Deployment and client isolation](05-client-isolation.drawio) — separate application installations and databases, client-scoped operational artifacts, and one reusable codebase. Boundaries do not imply separate physical machines.

## What is approved, what is proposed

- **Approved requirement:** each client has an independent application installation **and independent database**; separate schemas within a shared client database are insufficient. No shared client appointment store is proposed. Physical hosting remains open. [Architecture §3](../ARCHITECTURE.md#3-installation-and-database-isolation).
- **Approved behavior:** SDD-006 requires a common final integrity boundary and truthful success, rejection and unknown outcomes. SDD-005 supplies scheduling constraints; SDD-022 governs configuration impacts on accepted appointments. [SDD-006](../../specs/SDD-006-SHARED-BOOKING-INTEGRITY-AND-AUTHORITATIVE-OUTCOMES.md), [SDD-005](../../specs/SDD-005-AVAILABILITY-RESOURCE-CAPACITY-AND-SCHEDULING-POLICY.md), [SDD-022](../../specs/SDD-022-ACCEPTED-APPOINTMENT-CONFIGURATION-IMPACT.md).
- **Provisional direction:** a modular monolith per installation and the preferred Laravel / Blade / Tailwind / MariaDB stack are accepted directions, not final architecture, installed dependencies or implementation approval. [Architecture §2](../ARCHITECTURE.md#2-provisional-architecture-direction), [TRD](../../technical/TRD.md).
- **Database status:** [BACKEND_SCHEMA.md](../BACKEND_SCHEMA.md) is an accepted provisional *conceptual* information-model reference, not an approved physical schema. The archived [Data Architecture & Model Design](../../archive/legacy-sdlc/architecture-working-designs/DATA_ARCHITECTURE_MODEL_DESIGN.md) contains 25 logical candidates and an earlier conceptual ERD; D-088 gave its fingerprinted design a limited provisional working-design disposition, not table or migration approval. Its account-free assumptions predate the approved account amendment. The [archived component design](../../archive/legacy-sdlc/architecture-working-designs/COMPONENT_MODULE_DESIGN.md) has a similarly bounded D-086 disposition. Do not read retained old draft labels in isolation.
- **Baseline:** [requirements v0.9](../../requirements/REQUIREMENTS-SPECIFICATION-v0.9.md), with [v0.8](../../requirements/REQUIREMENTS-SPECIFICATION-v0.8.md) and unchanged [v0.7](../../requirements/REQUIREMENTS_SPECIFICATION.md), are approved development-stage requirements, not stakeholder-validation or implementation evidence. Current SDD revisions and approvals are recorded in [SDD Registry §13](../../specs/SDD_REGISTRY.md#13-current-approval-summary). This proposal does not change them.

## Candidate core data dictionary

All IDs below are installation-local. Required versus nullable and data types are proposed, not decided; choose exact types, lifecycle, retention, indexing and access controls in later authorized physical design. Required FKs below are non-null; `?` marks a nullable field. `UQ` denotes proposed uniqueness. The association-specific proof reference represents evidence, **not** the proof mechanism or a bearer credential.

| Candidate table | Candidate columns / constraints | Relationship and purpose |
|---|---|---|
| `service` | `id` PK; `name`, `duration_minutes`, `active` | One service → zero or many appointments and schedule rules. Duration is per service; buffers and policy need further representation. |
| `schedule_rule` | `id` PK; `service_id` FK; `rule_definition`; `effective_from`, `effective_to?` | Each candidate rule belongs to one service; recurrence, exceptions, resource-scoped rules and effective versions remain open. |
| `appointment` | `id` PK; `service_id` FK; `reference` UQ; `start_at`, `end_at`, `status`, `created_at` | Each appointment has one service. Reference is unique within the installation; it is a lookup identifier, not authority. State vocabulary and time representation remain open. |
| `participation` | `id` PK; `appointment_id` FK; `role`, `scoped_details` | One appointment → one or more participation records, with booker and intended attendee contexts distinguished even if the same person. Number of attendees and personal-data representation remain open. |
| `resource` | `id` PK; `kind`, `label`, `configured_limit`, `active` | Staff/physical resource candidate; how a staff principal maps to a resource and how service requirements are configured are open. |
| `resource_allocation` | `id` PK; `appointment_id` FK; `resource_id` FK; `starts_at`, `ends_at`, `units` | One appointment and one resource per row; either may have zero or many allocations. A stored ledger is only a candidate; service/time capacity is an additional constraint and cannot be inferred from resource allocations alone. Buffer intervals and multiple allocations remain design questions. |
| `customer_account` | `id` PK; `account_state`, `verified_contact_ref?` | Optional installation-local account; sign-in, verification and credential storage are not specified. |
| `account_appointment` | `id` PK; `account_id` FK; `appointment_id` FK; `authorized_at`, `proof_evidence_ref`; UQ (`account_id`, `appointment_id`) | Each row connects one account and one appointment; each side can have zero or many rows as a **candidate**. The pair constraint prevents duplicate rows only. Actual allowed relationships and proof, revocation and history design need review; personal-data matching or reference alone is insufficient. |
| `booking_intent` | `id` PK; `intent_key` UQ; `operation`; `target_appointment_id?` FK; `result_kind?`; `created_at`; `result_appointment_id?` FK | One intent references zero or one target and zero or one result appointment; each appointment can be referenced by many intents. A null result does not itself prove a particular real-world outcome. This is a candidate correlation model, not a selected idempotency protocol; equivalence, authority, collision handling, result retention and recovery are open. |
| `appointment_event` | `id` PK; `appointment_id` FK; `event_kind`, `actor_ref`, `occurred_at`, `evidence_ref?` | One appointment → zero or many events; candidate consolidated history for changes/attendance. Actor referential integrity and audit representation are unresolved; this row does not replace required security or audit evidence. |

**Deliberate scope boundary:** staff principals and permissions, guest proof, MFA, configuration revisions, service-resource requirements, capacity periods, required audit, exception and dispute records, notification recovery, roster snapshots and reconciliation items are required *concerns*, but their tables, fields and links are not sufficiently decided to present as a complete schema here. They must be modeled during authorized design. An `actor_ref`, `evidence_ref` or `rule_definition` is a placeholder, not a claim that a free-form column can meet those obligations. No cross-client tenant identifier, payment, customer masterlist, or penalty table is introduced.

## Booking invariants and candidate transaction

1. All applicable booking-affecting paths recheck current authority, state, effective policy, eligibility, service/time capacity, resource constraints and duplicate rules. A previously shown slot is not reserved. Duplicate checks use approved attendee/eligibility criteria for the same service and effective window, not the booker alone. Exclusive resources cannot overlap and shared limits must be configured. [SDD-006 §§Shared final checks](../../specs/SDD-006-SHARED-BOOKING-INTEGRITY-AND-AUTHORITATIVE-OUTCOMES.md#shared-final-checks).
2. A candidate transaction coordinates appointment, capacity effects and required audit with the authoritative outcome. A known rejection leaves no partial/orphaned effects; a rejected reschedule preserves the original appointment and allocation. Concurrent configuration changes must also be accounted for. Atomicity is required; exact lock domain, transaction isolation, schema, audit consistency, conflict and deadlock handling are open. A unique reference or intent key **does not** enforce interval overlap, aggregate capacity or duplicate policy. [TECH-WP-02 booking](../../technical/TECH-WP-02-BOOKING.md).
3. A lost response is **unknown**, not success or failure. Establish the result for the same intent before an unsafe retry or confirmation. Email for an established transaction follows the committed outcome; failure to deliver does not reverse it or repeat the command. Permitted purposes and recipients are constrained by [SDD-007](../../specs/SDD-007-SIX-PURPOSE-EMAIL-BOUNDARY-AND-DELIVERY-RECOVERY.md).
4. Authorized exceptions relax only specifically permitted controls with reason and evidence; they are not a general integrity bypass. Changes to configuration that might affect accepted appointments require the SDD-022 impact process. QR/reference lookup is separate from identity verification, change authority and attendance.
5. Future D-070 verification: **50 valid concurrent requests for one remaining capacity unit → exactly one success**, 49 safe unsuccessful outcomes, and no overcapacity, prohibited duplicates, partial or orphaned bookings. Define duplicate-policy and valid-request preconditions. This is not a measured result or latency target.

## Stack sufficiency and interactions

The preferred stack is a plausible starting point for the stated scale and server-rendered workflows, **subject to concurrency, accessibility, security, compatibility and operational verification**; no current test proves sufficiency. PHP runs Laravel on a web server; Laravel receives requests, applies server-side authority and booking policy and reads/writes the client database. Blade produces HTML, Tailwind supplies CSS, and browser JavaScript can improve interactions while final decisions remain on the server. MariaDB provides relational persistence and candidate transactional capabilities, but naming it or using transactions alone does not establish safe concurrency. A web server/PHP runtime, secure network transport, database engine, suitable backups and restore processes, and a means to deliver the approved email purposes are operational capabilities; their precise products or arrangements remain open.

Git and automated testing support development rather than runtime booking. Node-based asset tooling may be useful for building Tailwind assets, depending on the eventual supported build process; it is not necessarily a production runtime. Alpine, Livewire, React/Vue, Redis, a separate queue, Docker, calendar/scanner libraries, cloud platforms and a specific email vendor are optional candidates, not prerequisites or selected dependencies. Durable notification recovery is a behavioral concern; it does not automatically mandate a separate queue or outbox. D-113/D-114 describe a **conditional local foundation direction**, not a verified product-wide dependency baseline; see [foundation review](../../technical/FND-PREREQUISITE-REVIEW.md).

## Material decisions for implementation review

1. **Policy and conflict domain:** service/time capacity units, resource assignment and buffers, attendee duplicate criteria and windows, and approved exception rules. Select and verify a concurrency design that covers all competing writers and configuration changes.
2. **Physical data and history:** decide which core candidates are stored or derived, relationship/cardinality details, policy versions, state transitions, audit consistency, retention and privacy boundaries.
3. **Authority and recovery:** determine internal permissions and MFA/recovery, appointment-scoped guest proof, account association and contested cases; ensure references/QR do not grant authority.
4. **Outcome and notification recovery:** decide same-intent identity/equivalence, authorized lookup and retention, unknown-outcome handling, and delivery persistence, retry and provider arrangements.
5. **Operational profile:** decide supported runtime/build versions, hosting and credential custody, backup/restore and real-backup verification, monitoring, and client/provider responsibilities. D-117's minimum allocation applies; detailed assignments and recovery targets remain open.

Specialist security/privacy and data-integrity reviews, synthetic integrated testing, and separate implementation and operational authorizations remain necessary. These diagrams are not a substitute for those reviews.
